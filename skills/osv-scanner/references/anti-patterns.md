## Anti-patterns

- **Don't** put flags after the positional directory with `-r`. At 1.9.2 the CLI stops parsing flags at the first positional, so `osv-scanner -r /scan --format json` tries to scan a directory literally named `--format` and exits `127`. Put every flag before `-r <dir>`: `osv-scanner --format json --output $HOME/osv.json -r /scan`. (`-L <file>` consumes its value, so trailing flags happen to work there — do not rely on it.)
- **Don't** scan `node_modules` instead of `package-lock.json`. Lockfiles have *resolved* versions and pin transitive deps; `node_modules` is huge, slow to walk, and may have hoisted/deduped layouts that mislead version detection. Always point at the lockfile.
- **Don't** add an `[[IgnoredVulns]]` entry without `ignoreUntil`. The 1.9.2 file format treats the field as optional, which makes forever-ignores easy — a year later the upstream patch exists, the dep is fixable, and nobody knows because the scanner stopped complaining. Harness policy is a date + reason on every ignore, re-reviewed before expiry.
- **Don't** rely on `package.json` / `Cargo.toml` / `requirements.txt` *manifest* files for vulnerability data. They list constraints, not resolved versions. Only the lockfile (or an SBOM) tells you which exact versions are installed and therefore exposed. Maven `pom.xml` is the exception — 1.9.2 resolves it by default — but that resolution needs deps.dev egress, so prefer a lockfile or SBOM in the sandbox.
- **Don't** use `--experimental-no-resolve` on a fresh Maven/Gradle checkout without confirming a lockfile or SBOM exists. You'll get a green-looking result because *nothing was scanned*. Verify by running once with resolution enabled and comparing finding counts, or by reading the source count in the JSON.
- **Don't** treat exit `128` as clean. It means no packages were found — a wrong path, an unsupported file, or a bad parser override. Fix the target and rerun.
- **Don't** treat exit `129` as "no vulnerabilities". It is an API/networking failure, the normal shape of egress denial when `api.osv.dev` is unreachable. Fix connectivity or the allowlist and rerun; do not report the scan as clean.
- **Don't** swallow exit code `1` with `|| true` to make CI green. That's the entire signal. Fix the dep, ignore the vuln with `ignoreUntil`, or document the exception — but don't silence it.
- **Don't** paste the raw JSON report into your answer. It is large and mostly advisory noise. Select the source/package/version/ID rows with `jq` and cap them with `head`.
- **Don't** confuse osv-scanner with secret scanners or SAST. It only knows about *published* vulnerabilities in *known versions* of *packaged dependencies*. It will not find a hand-rolled SQL injection (use `semgrep` / `opengrep`), a leaked API key (use `gitleaks` / `trufflehog`), or a vulnerable internal library with no public advisory.
- **Don't** wait for release time to scan. osv-scanner runs in seconds for typical lockfiles — gate every PR. Replacing several per-ecosystem audits with one binary makes this cheaper, not more expensive.
